4. **V2 有几条承诺技术上站不住**。详见 5.4 节的可行性重判，其中「应用数据备份还原」在无 root 条件下**基本不可实现**，必须如实降级。

## 2. 三代产品定位

### 2.1 一句话定位

**从「看得清、能卸载的列表工具」，升级为「设备应用治理中枢」——看得见空间去哪了、清得掉垃圾、管得住行为、救得回来、管得动更多设备。**

### 2.2 定位升级的三个支点

| 支点 | 一代 | 三代 |
|---|---|---|
| 深度 | 能看能卸 | 能清能控（清理闭环 + AppOps 管控） |
| 权限上限 | 普通权限为主 | 四级台阶：普通权限 → Shizuku → Device Owner → Root |
| 边界 | 手机单机 | 手机 + PC 双端，单机 → 多设备面板 |

### 2.3 目标用户与对应能力

| 画像 | 核心诉求 | 三代对应能力 |
|---|---|---|
| 空间焦虑型（128G 机型） | 找出并清掉占空间的僵尸应用与垃圾 | 存储分项可视化 + 残留/垃圾扫描 + 应用归档 + 闲置标记 |
| 洁癖整理型 | 清预装、去广告 SDK、收敛权限 | Shizuku 系统应用治理 + 应用冷冻 + 跟踪器识别 + 权限批量回收 |
| 效率管理型 | 知道自己时间花在哪个 App | 使用统计 + 启动次数/时长排行 + 单应用限时 |
| 保守惜命型 | 怕误删，想留退路 | 操作日志 + 撤销 + APK 备份 + 误删急救包 + 应用归档（第三态） |
| 批量运维型（新增） | 一次配好一批机器 | Device Owner 专业版 + PC 端 ADB 通道 + 多设备面板 |

### 2.4 与非同类工具的差异点

1. **卸载之外的第三态——应用归档**：整体打包冷存，用时还原。比卸载安全、比保留省空间，同类工具普遍未做透。
2. **可恢复的系统应用治理**：免 root「针对当前用户卸载」+ 隐藏 + 一键全部还原，系统分区不动、OTA 正常。
3. **清理闭环**：从「看得见占用」到「清得掉残留」，串联存储、垃圾、残留、专清四层。
4. **静默通道可选升级**：Device Owner 模式提供无弹窗批量操作，同一套代码覆盖个人用户与批量运维。
5. **完全离线**：核心能力不申请网络权限，全部本地处理。

## 3. 能力分层模型（L0–L6）

| 层级 | 权限/能力 | 获取方式 | 解锁功能 |
|---|---|---|---|
| **L0 基础** | 无 | 安装即用 | 列表、详情、启动应用、分组标签、操作日志 |
| **L1 全量列表** | `QUERY_ALL_PACKAGES` | 普通权限，安装即授 | 看到全部已安装应用而非仅带 launcher 的 |
| **L2 卸载用户应用** | `REQUEST_DELETE_PACKAGES` | 普通权限 | 单个/批量卸载（系统弹窗确认） |
| **L3 数据权限** | `PACKAGE_USAGE_STATS` / `MANAGE_EXTERNAL_STORAGE`（可选） | 跳系统设置手动开启 | 使用统计、闲置识别、全盘垃圾扫描、崩溃记录 |
| **L4 Shizuku** | Shizuku 服务（无线 ADB 或 root 启动）+ `moe.shizuku.manager.permission.API_V23` | 运行时授权 | 系统应用卸载/还原、应用冷冻、AppOps 管控、自启管理、权限批量回收、静默清缓存、残留深挖 |
| **L5 Device Owner** | `adb shell dpm set-device-owner` | 一次性 ADB 命令（无需 root） | 静默安装/卸载、静默授权、静默隐藏/停用、Kiosk、策略下发 |
| **L6 Root** | Magisk / KernelSU 授权 | 用户刷入 | L5 全部 + 组件 block、分区读写、Magisk 模块管理、`build.prop` |

### 3.1 设计原则

- **渐进解锁**：没有对应权限的功能显示为「需开启 XXX」，点击引导到授权路径，**绝不静默失败**。
- **能力状态单一真源**：`core/permission` 暴露 `Flow<Set<Capability>>`，UI 只订阅不自行 `if` 判断。
- **危险操作硬约束**：
  - 系统分区只读，一切操作走 `--user 0`，保证 OTA 与保修不受影响。
  - 「关键」级应用（SystemUI / 电话 / 桌面 / 输入法 / 设置）永不提供卸载入口，仅允许停用。
  - 影响面 > 5 个包的批量操作，二次确认弹窗必须列出全部目标包名。
  - 所有提权操作写入审计日志，提供一键还原。

## 5. 功能模块详细设计

### 批次一 · 存储与清理闭环【P0】

#### B1 存储空间可视化

**目标**：回答「空间去哪了」。

- 应用详情页存储分项：APK、数据、缓存、外部数据、AOT 编译产物、引导配置档。
- 列表支持按「占用大小」排序；顶部汇总「用户应用合计 / 系统应用合计 / 缓存合计」。
- 全局存储页：卷总容量、已用、可用；横向分段柱状图。
- Android 15（API 35）启用 `StorageStats.getAppBytesByDataType()` 做更细拆分，低版本自动降级为 `appBytes / dataBytes / cacheBytes` 三项，UI 按版本条件渲染。

**技术要点**

```kotlin
suspend fun queryAppStorage(pkg: String): StorageUsage = withContext(Dispatchers.IO) {
    val ssm = context.getSystemService(StorageStatsManager::class.java)
    val uuid = context.getSystemService(StorageManager::class.java)
        .getUuidForPath(context.filesDir)              // 必须用真实路径拿卷 UUID
    val stats = ssm.queryStatsForPackage(uuid, pkg, Process.myUserHandle())
    StorageUsage(
        appBytes = stats.appBytes,
        dataBytes = stats.dataBytes,
        cacheBytes = stats.cacheBytes,
        externalDataBytes = stats.externalDataBytes,
        aotBytes = if (Build.VERSION.SDK_INT >= 35)
            stats.getAppBytesByDataType(
                StorageStatsManager.APK_DATA_TYPE_FILE_TYPE_DEXOPT_ARTIFACT
            ) else null,                                // 低版本为 null，UI 不显示该行
    )
}
```

- 统计查询是 Binder 调用，**必须**在 IO 线程批量化；一次查询缓存 60s，key = `uid + versionCode`。
- 仅需 `QUERY_ALL_PACKAGES`，无需 root。

**验收**：与系统设置「存储-应用用量」总量误差 ≤ 2%；200 应用统计在 60s 缓存未命中时 ≤ 3s，无主线程掉帧（< 5%）。

#### B2 使用统计与闲置识别

**目标**：回答「哪些该卸」。

- 采集：最后使用时间、前台总时长、启动次数。
- 列表支持按「最后使用时间 / 使用时长 / 启动次数」排序。
- 闲置识别：连续 30 天未启动 → 打「闲置」标签，筛选器一键筛出；叠加「占用 > 100MB」生成清理建议。
- 排行页：本周/本月使用时长 Top 20、启动次数 Top 20。
- 单应用限时（P2）：设定每日可用时长，超时提示（不做强制拦截）。

**技术要点**

- 特殊权限 `android.permission.PACKAGE_USAGE_STATS`，通过 `Settings.ACTION_USAGE_ACCESS_SETTINGS` 授予，**非运行时弹窗**。
- 入口：`UsageStatsManager.queryUsageStats()` / `queryEvents()`；`ACTIVITY_RESUMED` 事件推算启动次数。
- **降级铁律**：无权限时 API 返回空列表，UI 必须显示「无数据」并整体隐藏该功能区，**禁止兜底为 0**——否则会把所有应用误判为闲置，这是最严重的一类误伤。

```kotlin
// 闲置判定（注意 elapsedRealtime 与 wall clock 混用陷阱）
val idle = lastUsedElapsedRealtime == 0L ||
    SystemClock.elapsedRealtime() - lastUsedElapsedRealtime > IDLE_THRESHOLD_MS
```

**验收**：授权后 5s 内出排行；未授权时功能区整体隐藏而非报错。

#### B3 垃圾与残留扫描【V3 新增，核心留存点】

**目标**：从「看得见占用」走到「清得掉垃圾」。

| 子功能 | 扫描对象 | 所需能力 |
|---|---|---|
| 卸载残留 | `/sdcard/Android/data/<pkg>`、`/sdcard/Android/obb/<pkg>`、`/sdcard/<AppName>` 同名目录（应用已不在包列表） | L4 Shizuku（shell 可读 `Android/data`）或 L3 `MANAGE_EXTERNAL_STORAGE` |
| 空目录与碎片 | 递归扫到的空文件夹、仅含 `.nomedia` 的目录 | L3 / L4 |
| 缩略图与日志残留 | `Android/data` 下 `cache/`、`thumbnails`、`*.log`、`crash/` 目录 | L3 / L4 |
| 大文件面板 | 全盘 > 100MB 文件按大小排序（与应用占用互补的两个视角） | L3 `MANAGE_EXTERNAL_STORAGE` |
| 重复文件 | 按「大小预筛 → 首尾 4KB 哈希 → 全文 SHA-256」三级比对 | L3 |
| 社交专清 | 微信 / QQ / TIM / 抖音 / 钉钉 的缓存与可清理文件分类 | L3 / L4 |

**技术要点**

- Android 11+ 应用自身**无法**读取其他应用的 `Android/data/<pkg>`（Scoped Storage）。两条可行路径：
  1. `MANAGE_EXTERNAL_STORAGE`（`Settings.ACTION_MANAGE_ALL_FILES_ACCESS_PERMISSION` 引导）——权限敏感，需在应用内明示用途；
  2. Shizuku 下以 shell UID 执行 `ls` / `stat` / `rm` —— shell 对 `/sdcard/Android/data` 有读权限，这是更干净的路径。
- 删除一律走「先扫描出清单 → 用户勾选 → 二次确认 → 执行」，**不做一键无脑全清**。
- 每个条目显示「来源应用 / 路径 / 大小 / 最后修改时间」，可长按加入白名单（白名单持久化到 Room）。
- 所有删除写审计日志，保留 7 天可回溯。

**验收**：残留识别准确率（对照 `pm list packages` 差集）≥ 98%；扫描 6 万文件 ≤ 8s 且可中断。

#### B4 应用归档【V3 新增，差异化】

**目标**：提供卸载之外的**第三态**——保留能力、释放空间。

- 归档 = 把「APK 全部分片 + 清单元数据（包名/版本/安装时间/权限快照/来源）」打包为 `.kaz` 文件，存入外置存储或导出到 PC。
- 归档后可选自动卸载应用本体，空间立即释放；列表中以「已归档」态展示（灰显 + 归档图标）。
- **一键还原**：从归档包静默或半静默装回（L4/L5 下可无弹窗），并恢复权限快照。
- 归档库管理页：总占用、按时间排序、批量删除、校验完整性（SHA-256）。
- 归档触发建议：闲置 > 90 天 且 占用 > 200MB 的应用，在清理建议中提示「归档而非卸载」。

**技术要点**

- APK 分片清单来源：`ApplicationInfo.splitSourceDirs` + `splitNames`；`getPackageArchiveInfo` 拿不到全部分片。
- 归档包结构（zip，无压缩存储大文件以利于随机读）：

```
com.tencent.mm.kaz
├── manifest.json          # 包名、versionCode、versionName、firstInstallTime、
│                          # 权限快照、屏幕密度、ABI、归档时间、SHA-256
├── apks/
│   ├── base.apk
│   └── split_config.arm64_v8a.apk ...
└── README.txt             # 还原方法与限制说明
```

- 大包归档在 `WorkManager` 后台执行，通知栏显示进度；单应用归档上限 4GB（防空间耗尽）。
- **限制如实声明**：还原到「应用已存在的环境」时，因签名一致性问题，**不保证原位覆盖**；归档的用途是「装到没有该应用的环境」。

**验收**：归档 → 卸载 → 还原全链路在 Android 11/14/15 各机型通过；归档包 SHA-256 校验一致。

### 批次二 · 治理与管控中枢【P0】

#### B5 批量治理中心

**目标**：把「逐个点」变成「有序批」。

- 多选增强：按筛选结果全选、按条件批量选择（如「全部闲置 且 > 200MB」）、按标签选。
- 批量动作：卸载、归档、清理缓存、清理残留、导出备份、加入待清理清单。
- 风险分级（四级，规则来自内置知识库且**用户可编辑**）：

| 级别 | 含义 | 处理策略 |
|---|---|---|
| 推荐 | 明显冗余，卸载无副作用 | 一键批量卸载，默认选中 |
| 高级 | 需谨慎，删除后可能影响功能（厂商服务、输入法扩展等） | 逐个确认，展示依赖提示 |
| 关键 | 卸载可能导致桌面/电话/系统服务异常 | 默认禁止，折叠在「高级模式」开关后 |
| 系统 | 分区系统应用 | 显示可用操作（隐藏 / 停用 / 针对当前用户卸载） |

- 操作审计日志（Room）：时间、包名、动作、结果、耗时；支持「撤销本次批量卸载」。

**验收**：批量 50 个应用不 ANR，进度可视、可中断、可继续；每条日志可回溯。

#### B6 应用冷冻【V3 新增，玩家刚需】

**目标**：在不卸载的前提下让应用彻底休眠。

| 能力 | 路径 | 说明 |
|---|---|---|
| 停用应用 | `pm disable-user --user 0 <pkg>`（L4）或 `setComponentEnabledSetting(DISABLED_USER)`（L2/L4） | 应用停止运行、不再接收广播 |
| 隐藏图标 | `pm hide <pkg>`（L4，部分 ROM） | 桌面不见，但包仍在 |
| 冻结与唤醒 | 冷冻后提供快捷方式/通知栏磁贴一键解冻 | 磁贴用 `TileService` |
| 数据保留 | 冷冻不触碰数据目录 | 解冻后登录态与数据完整 |

**技术要点**

- 免 Shizuku 的降级路径：`setComponentEnabledSetting(pkg, DISABLED_USER, DONT_KILL_APP)` 能停用整个应用包（把包名本身作为 ComponentName），覆盖大多数场景；Shizuku 路径可越过部分 ROM 的用户确认限制。
- 冷冻列表统一管理页：状态、冷冻时间、一键解冻、批量解冻。
- **红线**：当前启动器（桌面）、输入法、SystemUI、电话 永不允许冷冻。

**验收**：冷冻后该应用不出现在最近任务、不再有通知；解冻后数据完整。

#### B7 AppOps 管控【V3 新增】

**目标**：比权限更细粒度地控制应用行为。

- 可管控项：后台运行、后台定位、剪贴板读取、悬浮窗、读取通知、身体传感器、开机自启、安装其他应用、修改系统设置。
- 界面：应用详情页新增「行为管控」区，每项三态开关（允许 / 忽略 / 拒绝）+ 当前取值来源。
- 全局反查：按管控项维度列出「哪些应用被允许后台运行」→ 批量关掉。

**技术要点**

- Shizuku 通道：`Shizuku.newProcess(arrayOf("cmd", "appops", "set", pkg, op, "deny"), ...)`。
- 读取当前值：`AppOpsManager.unsafeCheckOpNoThrow(op, uid, pkg)`（API 29+），`MODE_ALLOWED / MODE_IGNORED / MODE_ERRORED`。
- 普通权限可读不可写；写入必须 L4+。
- 所有改动记录原值，支持「恢复默认」。

**验收**：改动后行为生效（例如切断后台运行后该应用不再有后台流量）；一键恢复默认可用。

#### B8 权限批量回收与默认应用管理

- **按权限维度反查**：选定权限（如麦克风）→ 列出所有已授予的应用 → 批量回收。
- Shizuku 通道：`pm revoke <pkg> <permission>` / `pm grant <pkg> <permission>`。
- **默认应用管理**：浏览器 / 桌面 / 短信 / 电话 / 数字助理的当前指向与候选列表，通过 `RoleManager`（API 29+）查询并用 `createRequestRoleIntent` 发起变更。
- **权限快照 diff**：每次进入详情页记录危险权限集合，diff 出「最近新增了什么权限」——这是隐私类工具最有说服力的功能之一。

**验收**：批量回收后系统设置中该权限确为「已拒绝」；角色变更走系统确认流程。

#### B9 通知与自启管理

- **通知管理**：批量开关 `POST_NOTIFICATION`（AppOps `OP_POST_NOTIFICATION`）；近 7 天通知数量统计（**仅在用户手动开启通知使用权后提供**，不做静默监听）。
- **自启管理**：枚举声明了 `BOOT_COMPLETED` 接收器的包（`PackageManager` 查 receivers）→ 结合 AppOps 关闭开机自启 / 后台运行。
- **电池优化白名单**：查询与批量修改 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 状态，给出「哪些应用不该被优化」的建议。

**技术要点**

- 通知历史需要 `NotificationListenerService`，**二代明确「不申请」**，本条沿用：只在用户主动开启时提供，且必须在使用前展示数据用途说明并单独开关。
- 自启判定只是「声明了接收器」，不等于「实际会启动」——UI 文案必须写清楚，避免误导。

#### B16 误删急救包【V3 新增】

- 卸载前自动把该应用的 APK 分片集复制进「急救包」（可在设置页关闭）。

#### B17 数据备份可行性边界【V3 新增 · 技术诚实条款】

**必须如实声明：在无 root 的 Android 11+ 设备上，第三方应用无法备份其他应用的数据目录。** 原因链条：

1. `/data/data/<pkg>` 权限为 `0700`，属主是该应用自己的 UID；
2. Shizuku 提供的 shell UID（2000）对该目录**没有读权限**，SELinux 亦无相应规则；
3. `adb backup` 自 Android 12 起被 Google 实质性废弃；
4. `run-as` 仅对 `debuggable=true` 的应用有效。

因此三代的能力边界是：

| 场景 | 是否可行 | 路径 |
|---|---|---|
| 备份 APK（本体） | ✅ 可行 | 批次四 B15 |
| 备份应用数据 | ❌ 无 root 不可行 | 只能引导用户用应用自带的「导出/迁移」功能 |
| 备份应用数据（Root） | ⚠️ 技术可行但高风险 | L6 `tar` 打包 `data/data/<pkg>`；需完整声明风险且默认隐藏 |
| 整机数据迁移 | ✅ 可行（系统能力） | 引导至系统「手机搬家」/ 厂商迁移工具 |

**产品处理**：不做虚假承诺。备份页明确区分「可备份：安装包」「不可备份：应用数据（系统限制）」，并提供「引导用户用应用内自带导出功能」的分步说明。这一条是对 V2 方案 M5 的**修正**。

#### B18 手机搬家

- 导出「搬家包」（`.kmpkg`）：应用清单（含包名/版本/归档状态）+ 归档包 + 自定义标签与规则 + 设置。
- 新机导入：解析清单 → 比对已有应用 → 列出差异（缺什么、多什么、版本落后什么）→ 一键批量安装缺失项。
- 跨端：搬家包可通过 PC 端中转（见批次六）。

### 批次五 · 提权升级【P1 / P2】

#### B19 Device Owner 专业模式【V3 新增，战略级】

**目标**：一次 ADB 配对后获得**完全静默**的批量操作能力，同时打开批量运维场景。

- 启用方式：`adb shell dpm set-device-owner com.yunlu.kongjian/.YunluDeviceAdminReceiver`（一次性，无需 root、无需刷机）。
- 能力对照：

| 能力 | 普通 / Shizuku | Device Owner |
|---|---|---|
| 安装 APK（含分片集） | 需用户确认 | **完全静默** |
| 卸载应用 | 需用户确认 | **完全静默** |
| 授予/回收运行时权限 | 逐个确认 | **静默**（`setPermissionGrantState`） |
| 隐藏 / 停用应用 | 部分受限 | **静默**（`setApplicationHidden` / `setPackagesSuspended`） |
| 白名单与 Kiosk | 不可用 | 可用（`setLockTaskPackages` / `setLockTaskMode`） |
| 策略下发 | 不可用 | 可用 |

- **诚实的待验证项**：静默卸载在不同 Android 版本与 ROM 上的可用 API 存在差异（部分版本需要走 `PackageInstaller` 的 DO 特权通道，部分 ROM 有额外限制）。**必须在 Android 11 / 14 / 15 三台真机上逐版本验证后**再对外声明该能力，验证不通过的版本自动降级为「Shizuku 半静默 + 用户确认」。
- 产品边界：Device Owner 模式与「单机工具」定位冲突（设置后系统限制卸载本应用的常规方式）。处理办法：
  1. 作为**独立入口**「专业模式」，默认隐藏，需在设置页连续点击版本号解锁；
  2. 启用前用全屏说明页列出影响与退出方法（`dpm remove-active-admin` 或恢复出厂）；
  3. 面向批量运维场景单独分发一个 flavor（`com.yunlu.kongjian.pro`），个人版不启用。
- 审计：所有静默操作强制写日志，「一键全部还原」为必备能力。

```kotlin
    suspend fun grantPermission(pkg: String, permission: String): Result<Unit>
    suspend fun silentInstall(apkSet: List<File>): Result<Unit>
    suspend fun deletePath(path: String, recursive: Boolean): Result<Unit>
}
```

**降级链**：`DeviceOwnerBackend` → `ShizukuBackend` → `RootBackend` → `NoOpBackend`。运行时按最高可用层选中，UI 只读 `capabilityFlow`。

### 6.3 关键数据流

```
列表加载：AppListViewModel → AppRepository.getApps(filters)
         → PackageManager.getInstalledApplications(GET_META_DATA)
         → Flow<List<AppInfo>> → UI

实时刷新：广播 PACKAGE_ADDED/REMOVED/REPLACED + 首帧主动同步（冷启动不丢）
         → AppRepository.appListInvalidator（MutableSharedFlow）
         → ViewModel 重新查询

清理闭环：CleanupScanner.scan(scope) → Flow<CleanItem>
         → 用户勾选 → CleanupExecutor.delete(items, backend)
         → 审计日志入库 → 刷新空间统计

卸载（L2）：UninstallUseCase
         → Intent(ACTION_DELETE, Uri.parse("package:$pkg"))
         → startActivityForResult → RESULT_OK / CANCELED
         → 归档急救包 → 审计日志 → 列表移除

卸载（L4/L5）：UninstallUseCase
         → backend.uninstallForUser(pkg, 0)  // pm uninstall -k --user 0
         → 可选 backupFirst → 审计日志
```

## 7. 权限与合规

### 7.1 权限清单

| 权限 | 层级 | 用途 | 是否敏感 |
|---|---|---|---|
| `QUERY_ALL_PACKAGES` | L1 | 列出全部已安装应用 | 政策敏感（Play 审核） |
| `REQUEST_DELETE_PACKAGES` | L2 | 调起系统卸载界面 | 否 |
| `PACKAGE_USAGE_STATS` | L3 | 使用统计、闲置识别 | 特殊权限，需手动开启 |
| `MANAGE_EXTERNAL_STORAGE` | L3（可选） | 全盘垃圾扫描 | **高敏感**，默认不申请，仅在用户选择「全盘扫描」时引导 |
| `WRITE_EXTERNAL_STORAGE`（≤ API 28） | — | APK 另存到「下载/云麓空间」 | 否 |
| `POST_NOTIFICATIONS` | — | 后台任务进度通知 | 否 |
| 网络权限 | — | **不申请**（核心离线）；更新检查为可选且默认关闭 | — |
| Shizuku API 权限 | L4 | 提权操作 | 运行时授权 |
| Device Admin（DO） | L5 | 静默操作（专业模式专属） | 需 ADB 一次性启用 |

### 7.2 隐私承诺（写入应用内与分发页）

1. 核心功能**不联网**，不采集、不上传任何数据。
2. 不申请 `MANAGE_EXTERNAL_STORAGE` 作为默认权限，仅在用户主动选择全盘清理时引导。
3. 通知统计需用户手动开启通知使用权，不做静默监听。
4. 所有提权操作可回溯、可撤销。

### 7.3 分发合规

- 渠道：GitHub Releases（主）+ F-Droid（备）+ 官网直链。
- 不上 Google Play（`QUERY_ALL_PACKAGES` 审核风险）；若未来上架，需准备 `<queries>` 白名单降级模式。
- 专业模式（Device Owner）单独 flavor 分发，避免影响个人版审核。

## 10. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| `MANAGE_EXTERNAL_STORAGE` 被判定为滥用 | 中 | 高（无法分发） | 默认不申请；优先用 Shizuku shell 通道做残留扫描；仅「全盘清理」引导时申请 |
| Shizuku 被 ROM 厂商限制 | 中 | 中 | 三态明确提示 + 降级到「仅停用」；文档给出各 ROM 适配说明 |
| Device Owner 静默卸载的版本/ROM 差异 | **高** | 中 | 逐版本真机验证后才对外声明；不通过的版本自动降级为半静默 |
| 垃圾扫描误删用户文件 | 中 | **高** | 只扫已知目录白名单；先列清单再删；白名单机制；审计日志 + 7 天可回溯 |
| 应用归档还原失败（签名/分片不全） | 中 | 中 | 归档时校验分片完整性 + SHA-256；还原前预检并明确提示 |
| 应用数据备份承诺落空 | **高** | 中 | 已在 B17 如实降级为「不可行」，不做虚假承诺 |
| 风险分级误判导致误删 | 中 | 高 | 规则来自公开知识库且用户可编辑/关闭单条规则；关键级硬禁用；二次确认 + 备份前置 |
| 图标缓存 OOM | 中 | 中 | LRU 上限 + 按需降采样到 96px + 内存压力回调清理 |
| 跟踪器字符串匹配误报 | 中 | 低 | 签名库条目人工复核后内置；UI 标注「仅供参考」 |
| 通知统计涉及隐私 | 中 | 中 | 仅在用户手动开启时提供，独立开关 + 用途说明 |

## 12. 假设与未验证项（如实声明）

1. 本方案基于 Android 官方文档与主流开源项目（App Manager / Canta / UAD / MobDirStat / Shizuku）的公开资料撰写，**未在真机上逐项验证**，各 ROM 实际行为需在 alpha 阶段实测校准。
2. **Device Owner 静默卸载的可用性未验证**：不同 Android 版本与 ROM 的 API 支持不一致，须在 Android 11 / 14 / 15 真机逐版本验证。
3. **无 root 下应用数据备份不可行**（B17），已如实降级，不作为交付承诺。
4. `getAppBytesByDataType` 仅 Android 15+，低版本分项粒度较粗，UI 需条件渲染。
5. 风险分级规则清单需按目标用户机型做统计校准；三代先以内置规则文件交付，规则可由用户编辑。
6. Shizuku 的 `pm uninstall -k --user 0` 在部分厂商 ROM 上可能被拦截或改写行为，V3.0.0 前必须完成 4 台真机验证。
7. 垃圾扫描在 Android 11+ 依赖 Shizuku shell 通道或 `MANAGE_EXTERNAL_STORAGE`，两条路径的实际成功率与 ROM 相关，需实测。
8. 跟踪器签名库的覆盖度与误报率未经实测校准。
9. 小组件与磁贴在国产 ROM 的后台限制下可能失效，需引导用户加白名单。
10. 目标平台为 Android；iOS 受沙盒限制不可行（依据初版方案 2.3 结论），不在本方案范围。
